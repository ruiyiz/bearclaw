Workflow Engine Design

Replace handlers and heartbeat with one primitive: a workflow, a small flowchart of typed nodes with explicit human-in-the-loop steps, run by a durable step interpreter in the host process, and managed from a first-class Workflows module in the web UI alongside Chat.

Problem

Today a "workflow" is a handlers row: one prompt, one agent run, one 500-character log line. Heartbeat is the same thing with a special prompt and a quiet window. What the codebase does not have shows up in the live handler prompts:

Gap Evidence
Structure lives in prose. Branches, guards and side-effect ordering are enforced by the LLM's obedience, not by the system. feed-triage is a six-step pipeline with a zero-unread branch, a "SEND GUARD" paragraph, and a rule that marking items read must happen only after a confirmed send.
Deterministic steps cost an LLM turn. feeds count, feeds unread, gws gmail +send, feeds read, pipeline.mjs next all run inside an agent with every tool enabled, bypassPermissions, and a 5-minute timeout.
No human-in-the-loop primitive. No ask_user, no approval gate, no canUseTool. Workarounds: newsletter-plan-ping "ends its turn, the brainstorm continues as normal chat"; feed-triage reply-by-number rides on the +main email poll; HEARTBEAT.md says "seek clarifications from the user".
Chaining is loose. handler_complete is emitted but nothing consumes it. emit_event has no authorization. Filters are exact-match JSON. No data flows between steps except through payloads or files. No run identity, so feed-triage-watchdog is a second, uncoordinated handler that infers the previous run's outcome from a file's mtime.
Cross-agent workflows are three handlers and a JSON file. Newsletter: newsletter-plan-ping (main) → skill queue file → newsletter-send (coco) → newsletter_queue_empty event → newsletter-empty-alert (main).
Observability is thin. handler_logs.result is 500 chars. events are purged after 24 h and take dependent logs with them. Admin UI: read-only list with pause/resume/delete, no create, no edit, no run view.
No tests. bus.ts, scheduler.ts, heartbeat.ts untested; initDatabase() hardcodes the path; config.ts throws without DEFAULT_MODEL.

Worth keeping: runContainerAgent (one-shot agent run with model, effort, session resume, timeout, streaming callbacks), the IPC message fan-out (primary channel resolution, per-agent authorization), the events table as a signal bus, cron-parser + TIMEZONE, the web broker/SSE plumbing, and the Agent SDK's outputFormat: { type: 'json_schema' } (available in the pinned SDK), which lets an LLM node hand typed data to a non-LLM node.

Concepts

Workflow: a definition file. Name, owner agent (default agent for LLM nodes), an inputs schema, nodes, edges, policies, and optionally declared triggers. Lives at ~/.bearclaw/workflows/<slug>.json. Files are the source of truth so the owner and the agent can edit them with ordinary file tools, they diff in git, and they match how skills and context files already work. A workflow is a function of its inputs; nothing in it depends on how it was fired.

Run: one execution of a workflow. Has an id, the trigger payload, a status (running | waiting | succeeded | failed | cancelled), and a context object that accumulates node outputs (nodes.<id>.output). Persisted to SQLite after every step so a restart resumes where it left off.

Node: an execution unit. Most nodes are not LLM calls.

Type What it does Output
agent One runContainerAgent call. Prompt template, agent folder override, model, effort, tools allowlist, max_turns, timeout, optional output_schema (SDK structured output; a success without structured output counts as a failure and retries), session mode fresh | run | chat, optional approve_tools (named tool calls pause the run as a human wait). text or typed JSON
shell Command with cwd/env/timeout; stdout parsed as json | text | lines. Non-zero exit is a failure. parsed stdout
http Request with method/url/headers/body. status + parsed body
template Mustache-style string rendering over the context. Replaces "ask the LLM to write HTML in this exact shape". string
transform Expression over the context producing a value. any
condition Boolean expression. Ports true / false. boolean
switch Expression producing a label. One port per case plus default. string
send Message or media to channel targets. Reuses the IPC fan-out (explicit jid, primary channel, or all). No LLM. delivery report
human Pauses the run and asks a person. Kinds: approve (approve/reject + comment), choice (labelled options), input (small form or free text). One port per action plus timeout. Targets, expiry (default 3 days) and on-timeout behaviour are configurable. the response, responder, responded_via
wait_event Pauses until an event matching a filter arrives. Matches events already persisted since the run started (or a lookback window), so a signal that lands before the node is reached is not lost. Ports received / timeout; a timeout is required. event payload
emit Emits an event onto the bus. event id
delay Durable sleep until a duration or wall-clock time. none
workflow Runs another workflow as a sub-run and waits for it. sub-run output
map Runs one node (or sub-workflow) per item of an array, with a concurrency cap. array of outputs

Edge: from → to leaving a named port. Every node has success and error ports; branching nodes replace success with their own (true/false, switch cases, human actions, received/timeout). port defaults to success, so a plain chain stays terse. Several edges from one port fan out in parallel; a node with several incoming edges joins, waiting for every incoming edge whose source node actually ran (edges from untaken branches never block; join: any is available for races). An unwired error port fails the run. Definitions must be acyclic; retry is a per-node setting, iteration is map. Canvas positions live in an optional top-level layout block, never in nodes, so the graph stays canvas-agnostic and auto-layout applies when the block is absent.

Trigger: a separate entity that binds a firing condition to a workflow and supplies its inputs. Stored as rows in workflow_triggers, never as state in the definition file. Types: cron (expression, timezone, quiet window, catch-up policy), event (type + filter, replaces register_handler), manual (dashboard button, /run <slug> in chat, MCP tool), webhook (POST /api/hooks/<token>, authenticated by token only), at (one-shot, replaces schedule_task run_at). Each trigger carries args, an object validated against the workflow's inputs schema; event and webhook triggers may map fields from their payload into args, and the raw payload stays available to nodes as trigger.payload. Triggers have their own enabled, next_run_at and last_run_id, so one cron can be paused without touching the workflow, and a run records which trigger fired it.

Two sources. A definition file may declare triggers[]; the loader upserts them with source: file and overwrites them on every reload, so the nightly cron lives next to the graph it drives and is versioned with it. Triggers created at runtime by the agent or the UI (a reminder for tomorrow, an extra webhook, a second schedule with different args) are rows with source: runtime and never touch the file. The split keeps mutable state (next fire time, one-shot reminders) out of git-tracked files while keeping the common case a single file.

The payoff is reuse. One reminder workflow with inputs: { text, to } and a single send node serves every "remind me tomorrow at 9"; the agent adds an at trigger with args instead of writing a workflow per reminder. The same feed-triage graph runs nightly from cron with { "limit": 15 } and on demand from chat with { "limit": 40 }.

Policies (workflow-level): concurrency: skip | queue | replace when a run is already active, alerts: { on_failure, on_missed } (replaces the watchdog pattern; on_missed fires when a cron run has not succeeded within expected_within of its slot), retention.

Heartbeat is gone as a concept. What it did (wake an agent on an interval with a standing brief, skip a quiet window, use a cheaper model) is an ordinary cron-triggered workflow with one agent node: the brief is the node's prompt, the quiet window is a property of the cron trigger, the model is a node setting, concurrency: skip prevents overlap. No heartbeat block in the registry, no HEARTBEAT.md convention, no HEARTBEAT_OK sentinel, no special-casing anywhere in the engine.

The default remains one workflow, one agent: owner sets the agent for every agent, send and human node unless a node overrides it. Cross-agent workflows are the same file with per-node agent overrides.

Definition format

Feed triage, rewritten from the current prose prompt into typed nodes: 

{
  "$schema": "bearclaw://workflow/v1",
  "name": "Feed triage",
  "slug": "feed-triage",
  "owner": "main",
  "inputs": {
    "type": "object",
    "properties": { "limit": { "type": "integer", "default": 15 } }
  },
  "triggers": [
    { "id": "nightly", "type": "cron", "cron": "0 20 * * *" },
    { "id": "manual", "type": "manual" }
  ],
  "policies": {
    "concurrency": "skip",
    "alerts": { "on_failure": "owner", "on_missed": { "trigger": "nightly", "expected_within": "2h" } }
  },
  "nodes": {
    "count":   { "type": "shell", "cmd": "feeds count --exclude-category aggregators", "parse": "json" },
    "unread":  { "type": "shell", "cmd": "feeds unread --json --newest --per-feed 3 --limit {{inputs.limit}} --exclude-category aggregators", "parse": "json" },
    "any":     { "type": "condition", "expr": "nodes.unread.output.length > 0" },
    "summarize": {
      "type": "agent",
      "model": "sonnet",
      "prompt": "Summarize each item in 1-2 sentences from its content field. Do not invent facts.\n{{json nodes.unread.output}}",
      "output_schema": { "type": "array", "items": { "type": "object",
        "properties": { "id": {"type":"number"}, "summary": {"type":"string"} }, "required": ["id","summary"] } }
    },
    "render":  { "type": "template", "file": "templates/feed-digest.html" },
    "send":    { "type": "shell", "cmd": "gws gmail +send --to {{env.OWNER_EMAIL}} --from ruiyizhang+main@gmail.com --subject {{q subject}} --body {{q nodes.render.output}} --html",
                 "retry": { "max": 2, "backoff": "30s" } },
    "persist": { "type": "shell", "cmd": "cat > ~/.bearclaw/var/agents/main/feed-batch.json", "stdin": "{{json batch}}" },
    "mark_read": { "type": "shell", "cmd": "feeds read {{join nodes.unread.output.*.id ' '}}" },
    "caught_up": { "type": "shell", "cmd": "gws gmail +send --to {{env.OWNER_EMAIL}} --from ruiyizhang+main@gmail.com --subject 'Feeds: all caught up' --body '<p>All caught up.</p>' --html" },
    "reply":   { "type": "human", "kind": "input", "to": ["email:main"],
                 "prompt": "Reply with: save 1 4 · summarize 7 · dismiss 2 · next", "expires": "7d" },
    "act":     { "type": "agent", "prompt": "Apply the user's reply to the batch: {{nodes.reply.output}}\nBatch: {{json batch}}" },
    "failed":  { "type": "send", "text": "Feed digest failed at {{error.node}}: {{error.message}}" }
  },
  "edges": [
    { "from": "count", "to": "unread" },
    { "from": "unread", "to": "any" },
    { "from": "any", "port": "true", "to": "summarize" },
    { "from": "any", "port": "false", "to": "caught_up" },
    { "from": "caught_up", "to": "persist" },
    { "from": "summarize", "to": "render" },
    { "from": "render", "to": "send" },
    { "from": "send", "to": "persist" },
    { "from": "send", "port": "error", "to": "failed" },
    { "from": "persist", "to": "mark_read" },
    { "from": "mark_read", "to": "reply" },
    { "from": "reply", "port": "submitted", "to": "act" }
  ]
}

Compared with the prose version: the send guard is an edge, the "write the empty batch file even when caught up" rule is an edge from caught_up into the same persist node, marking items read is structurally after a confirmed send, the LLM does exactly one thing and returns typed data, and the watchdog is a one-line policy. The reply node's unwired timeout port simply ends the run after seven days.

Templates use {{ }} with a handful of helpers (json, q for shell quoting, join, default). Expressions run in a node:vm context with a frozen { trigger, nodes, env, run, item, error } object, no globals, no Date/Math.random (use run.started_at), and a 50 ms budget. The sandbox is for determinism and accident containment, not security: the only authors are the owner and an agent that already has shell access. This is deliberately not a full language; anything that needs logic beyond a predicate belongs in a shell or agent node.

Engine

New module src/workflows/:

src/workflows/
├── schema.ts        zod schema for definitions; validation (acyclic, edge refs, unique ids)
├── store.ts         load/watch ~/.bearclaw/workflows/*.json; index rows; upsert file-declared triggers
├── engine.ts        run loop: ready-set computation, step execution, persistence, recovery
├── triggers.ts      trigger table: cron ticker, event subscription, webhook, one-shot `at`; args → inputs
├── waits.ts         human / event / delay waits; resolution; notification delivery
├── expr.ts          vm-sandboxed expressions + template rendering
├── executors/       one file per node type, each `execute(node, ctx, run, signal) → Result`
└── migrate.ts       handlers rows + heartbeat config → workflow files (one time)

Tables (in db.ts):

workflows         (slug PK, name, owner, enabled, file_hash, last_run_id, last_status)
workflow_triggers (id PK, slug, type, source 'file'|'runtime', config, args, enabled,
                   next_run_at, last_run_id, created_by, created_at)
workflow_runs     (id PK, slug, trigger_id, definition, definition_hash, run_key UNIQUE NULL,
                   inputs, trigger_payload, status, context, started_at, finished_at, error,
                   parent_run_id, forked_at_node)
workflow_steps    (id PK, run_id, node_id, attempt, status, input, output, error, log_path,
                   agent_session_id, started_at, finished_at)
workflow_waits    (id PK, run_id, node_id, kind, prompt, options, targets, notify_refs,
                   resume_at, on_timeout, token_hash, response, responder, responded_via, resolved_at)
workflow_events   (id PK, run_id, ts, node_id, kind, payload)      -- append-only timeline for the UI

Firing. triggers.ts owns one scan over workflow_triggers: cron and at rows by next_run_at, event rows by subscription on the events table, webhook rows by token lookup, manual rows by API call. Firing means: validate args (merged with any mapped payload fields) against the workflow's inputs schema, apply the workflow's concurrency policy, insert a run with trigger_id and inputs, and hand it to the decider. An at trigger disables itself after firing. A file-declared trigger whose id disappears from the file is deleted on reload; a runtime trigger is never touched by the loader.

Decider loop. A run advances by computing the set of nodes whose incoming edges are all satisfied, executing them (parallel where the graph allows), writing outputs into the context, and persisting. Anything that changes a run (a step finishing, a wait resolving, a timer firing) re-runs the decider over that run from persisted state; there are no long-lived coroutines to lose. A node that returns a wait flips the run to waiting. Large outputs above a cap are spilled to var/workflows/<run>/<node>.json and the context stores a reference.

Snapshot per run. A run copies the definition JSON into its own row when it starts and executes against that snapshot, so a wait that resolves a week later runs the graph it began with, even if the file changed. Editing the file affects new runs only; "replay on latest" is a separate action.

At-least-once, keyed. Every attempt gets a key <run>:<node>:<attempt>, exposed to shell as BEARCLAW_STEP_KEY, to http as a header, to agent in the prompt frame, and used by send to dedupe. Retry precedence is fixed: the node's retry policy exhausts first, then the wired error port, then the workflow-level on_error handler, then the run fails. Executors classify errors as retryable or fatal (a non-zero exit is retryable by default, a 4xx is fatal, an SDK structured-output miss is retryable with a stricter prompt).

Recovery. On boot, steps that were running are marked interrupted and re-dispatched under their retry policy; waits are untouched; delay and expiring waits are rows with a resume_at column, scanned on boot and on a coarse tick, never bare setTimeouts. Cron catch-up policy decides whether missed slots during downtime run once, run all, or are skipped.

Rerun from a node is a fork. Retry-from-X creates a new run with parent_run_id and forked_at_node, copies the completed step rows for X's ancestors, optionally overrides X's input, and starts the decider. Agent nodes in the fork resume from the parent's SDK session. Nothing is ever rewound in place.

Reuse. The agent executor calls runContainerAgent with outputFormat when a schema is set and with workflow metadata in the prompt frame so an agent node can still call send_message, emit_event and the new workflow tools. The send executor calls the same fan-out code as the IPC message watcher (extracted from index.ts into a function that takes a source agent and a target spec). The events table stays as the signal bus; triggers.ts and wait_event are its only consumers.

Human in the loop

A human node creates a wait, notifies, and parks the run. Three resolution paths, all writing the same workflow_waits.response:

  1. Web inbox. /inbox lists open waits with approve/reject buttons, choice buttons, or a form generated from the node's fields. Badge count in the top-level nav.
  2. Channel replies. Telegram gets inline keyboard buttons whose callback data is wf:<wait_id>:<choice>. iMessage, WhatsApp and email get the prompt as text, a short reply hint, and for approvals a signed one-shot link per action (/r/<token>, HMAC over wait id + action + nonce + expiry, single use, bound to the wait). The router checks for open waits targeting the inbound chat jid before dispatching to the agent; an exact match on a choice label or yes/no/approve/reject resolves the wait directly.
  3. Agent-mediated. Anything that is not an exact match goes to the chat agent as usual, with the open waits for that chat injected into its turn context, and the agent calls workflow_respond(wait_id, response). This is how free-text replies like "save 1 4, summarize 7" resolve an input wait without a parser per workflow.

Every resolution records responder (jid or web session) and responded_via (web | telegram | link | agent | timeout). Waits target people, not only the owner: to: ["imsg:17"] asks the kids a question and branches on the answer. Every wait has an expiry (default 3 days); on expiry the engine follows the timeout port if wired, otherwise applies on_timeout: approve | reject | skip | fail | { value }, otherwise fails the run. On restart, all pending waits are re-emitted to the SSE bus so the inbox is never stale.

Tool-level approval inside an agent node is a different feature from node-level approval, and both are needed. approve_tools: ["Bash"] on an agent node installs a PreToolUse hook that returns defer for matching calls: the query ends, the pending call becomes an ordinary wait row (kind tool, payload = tool input), and on approval the engine resumes the SDK session. canUseTool cannot be used for this because the SDK skips it under bypassPermissions, which the runner sets. AskUserQuestion from an agent routes through the same wait table so the inbox renders it as a form.

Replaces schedule_task, register_handler, list_handlers, pause_handler, resume_handler, cancel_handler, and the current_handlers.json snapshot.

Web UI restructure

Top-level modules, one nav for all of them (sidebar on desktop, tab bar on mobile):

Module Pages
Chat unchanged
Workflows /workflows list · /workflows/[slug] (graph, triggers, runs, definition editor) · /workflows/[slug]/runs/[id] (graph coloured by step status, live) · /workflows/events (bus log, moved from admin)
Inbox /inbox open human waits across all workflows, badge in nav
Schedules /workflows/schedules every trigger across workflows, sorted by next fire time, with file/runtime badge, pause, run now, and last-run status. This is the "all workflows, scheduled or otherwise" view; it lives under Workflows in the nav.
Admin agents, skills, context, health, transcripts (handlers and heartbeat pages removed)

The run view is the centre of the module: the same graph as the definition, nodes coloured by step status, a side panel with input/output/error/log for the selected node and a link to the agent transcript for agent nodes, and controls for cancel, retry from a node, and respond to a wait. Live updates arrive over the existing broker as a wf:* topic (run.status, step.status, wait.opened, wait.resolved).

Editing in v1 is the definition JSON in CodeMirror (already a dependency) with schema validation and a live graph preview that re-renders on every keystroke, the two views always in sync. A per-node form editor in the side panel is the v2 step, drag-and-drop on the canvas the v3 step; the file format is the contract either way, and the file stays hot-reloadable from disk so the owner or an agent can edit it outside the UI. Graph rendering uses @xyflow/react with @dagrejs/dagre for auto-layout, the one new UI dependency worth taking; ReactFlow state is derived at render time and never written back into the definition. Node config opens in a side sheet, not a modal. Lists and inbox are mobile-first; the canvas pans and zooms on touch.

Migration

migrate.ts runs once on first boot after the upgrade:

  • Every recurring or event handlers row becomes ~/.bearclaw/workflows/<id>.json with a single agent node carrying the old prompt, session: chat for context_mode: agent, and the cron or event trigger declared in the file with enabled from status. Pending one-shot reminders (the run_at handlers) become at triggers on the built-in reminder workflow with the old prompt as args.text; completed one-shots are skipped.
  • Each agent with a heartbeat block becomes <folder>-checkin.json: cron trigger from the interval with the quiet window, one agent node whose prompt is the current HEARTBEAT.md content, model from the old override, enabled from the old handler status (coco's is currently paused). The heartbeat block is then deleted from the registry.
  • handler_logs are left in place read-only until the retention window passes; the old tables are dropped in a later release.
  • Once migrated, the owner can refactor the prose workflows into typed nodes one at a time. Nothing forces that; a one-node agent workflow keeps working.

Removed: src/events/bus.ts, src/events/scheduler.ts, src/events/heartbeat.ts, the handler branches of processTaskIpc, the handler MCP tools, src/commands/jobs.ts (replaced by /workflows), the admin handlers and heartbeat pages, HeartbeatConfig in types.ts, HEARTBEAT_* in config.ts, the HEARTBEAT.md convention, the quiet-period special case in the bus.

Closest alternatives, and why build

Only two projects run inside a single Node process with local storage: Vercel Workflow DevKit (Apache-2.0, JSON files on disk, code-first with a build transform, no declarative graph, no run UI beyond a local inspector) and DBOS (MIT, but the TypeScript SDK requires Postgres). Both are workflow-as-code: the workflow is a function, and the graph exists only in the developer's head. That is the wrong shape here for two reasons. A definition an agent can write, validate and edit with file tools has to be data, and a run view that colours nodes by status has to know the graph before it runs. Everything else is a server (Temporal, Restate, Inngest, Hatchet, Kestra, Windmill, Conductor) or a product with its own UI, auth and storage (n8n, Activepieces, Dify, Sim), and would replace half of BearClaw rather than slot into it. The engine this design describes is a few hundred lines because it is a JSON DAG with persisted node outputs; the hard parts the servers solve (deterministic replay, history caps, process snapshots) do not arise when every node's result is a row.

Flowise's archive notice is the cautionary tale worth taking seriously: a rigid visual builder loses to a coding agent that can edit a text file. The definition format, the validator and the hot-reload from disk are the product; the canvas is a viewer first and an editor last.

Borrowed into this design

  • Named output ports instead of edge predicates (Sim connections: {success, error}, n8n's red error output, Dify's fail branch and one-branch-per-button Human Input). Every node has success/error; branching nodes define their own. Silent "continue on error" that passes input through unchanged (n8n's plain Continue) is deliberately not offered.
  • Graph keyed by stable ids with layout kept separate (Windmill OpenFlow, Node-RED flat array). n8n keys edges by node name so a rename rewrites every edge; Dify and Langflow dump ReactFlow state so every drag dirties git.
  • Decider loop over persisted state rather than long-lived coroutines (Conductor, Kestra, Windmill). Recovery on boot is "run the decider over every open run".
  • Per-node results keyed by (run, node, attempt), never re-executed once complete (Inngest, DBOS). No replay-determinism contract, no history caps.
  • Human wait = row + signed one-shot resume links + typed response schema + default timeout with explicit expiry behaviour (Windmill resume/cancel URLs and resume form, Kestra behavior enum, Dify's 3-day default, Mastra resumeSchema). Record who responded and via what (n8n "Capture Who Responded", Windmill approvers).
  • Buttons where the human already is (n8n Send-and-Wait on Telegram/Slack, Windmill interactive Slack approvals, Sim notifications). Telegram inline keyboard and keyword replies map to the same resolve path as the web inbox.
  • Interrupts addressed by id, resumed with a value map, re-emitted on restore (LangGraph __interrupt__, Microsoft Agent Framework pending requests, Strands). Never matched by position.
  • Persist signals before matching (Restate promises resolved before the waiter exists, Hatchet lookback). The Inngest failure mode, where an event that arrives before waitForEvent runs is lost, is avoided by matching wait_event against the already-persisted events table.
  • Timers as rows (DBOS durable sleep, Kestra pauseDuration): a resume_at column, scanned on boot and on a tick.
  • Retry precedence and fatal/retryable split (Vercel FatalError/RetryableError, DBOS shouldRetry, n8n's documented retry-vs-continue conflict).
  • Rerun from a node as a fork (Windmill restart-from-step, DBOS forkWorkflow, Conductor rerun, LangGraph time travel), combined with the SDK's forkSession for agent nodes.
  • Snapshot the definition into the run (Activepieces DRAFT/LOCKED versions, Kestra revisions, Microsoft AF's requirement of identical topology on resume). A wait that resolves days later runs the graph it started with.
  • Node-level and tool-level approval are separate features (OpenAI needs_approval vs Mastra suspend; Microsoft AF has both). The human node covers the first; approve_tools via the SDK's PreToolUse defer covers the second.
  • Typed handoff between LLM steps via structured output, not transcripts (LangGraph/Mastra typed state; the Claude SDK's own advice to pass results as application state rather than shipping transcripts). Only session_id and structured_output are stored per agent node.
  • Single payload per edge plus an explicit map (Node-RED, Windmill) rather than n8n's implicit item arrays. Map items get stable ids so fork and memoisation keys stay unambiguous (Windmill's restart-inside-loops bug), and failed items are kept as error entries rather than dropped (Claude SDK workflows, Dify iteration modes).
  • Concurrency policy per workflow and a unique run key for idempotent triggers (Kestra QUEUE|CANCEL|FAIL, Restate/DBOS workflow-id dedupe).
  • Triggers as separate entities binding args to a workflow's typed inputs (Windmill schedules and webhooks pointing at a flow path with their own args; Temporal Schedules; Conductor's external schedulers), with Kestra's convenience of declaring the common ones in the file. n8n, Sim, Activepieces and Dify make the trigger the root node, which ties the graph to one firing shape and makes "same workflow, different schedule and args" a copy.
  • Three synced views (Kestra: YAML, form, topology). v1 ships JSON + graph; the form editor comes second, drag-and-drop last.
  • Run timeline as an append-only event log (Temporal history, Hatchet event log) feeding the per-node UI.

Deliberately not borrowed

  • Replay determinism as a programming contract (Temporal, Vercel's sandboxed workflow context). Unnecessary when node outputs are rows.
  • Process snapshotting (Trigger.dev). Needs a supervisor; waits are explicit node boundaries here instead.
  • Item-array semantics on every edge (n8n). The largest learning-curve complaint about n8n.
  • Unbounded waits (Sim, Activepieces, Kestra without duration, LangGraph, OpenAI, Claude SDK). Every wait here expires.
  • Bearer links with no scoping (n8n link buttons, Dify email links, Sim portal URLs). Links here are signed, single-use, bound to one wait and one action, and the web inbox sits behind the existing session auth.
  • Out-of-process code sandboxes (n8n task runners, QuickJS in Windmill). The threat model has one author with shell access; node:vm is enough for determinism, and heavy logic goes in shell or agent nodes anyway.
  • Platform-gated basics (LangGraph's cron and inbox in LangSmith, AgentKit's HITL only inside Inngest). Scheduling and the SSE bus already exist in-process.

  3. Web module. Nav restructure, workflows list, run view with live graph and timeline, fork-from-node, inbox, JSON editor with synced graph preview. Admin handlers/heartbeat pages removed.

Each phase ships on its own; the system is usable after phase 2.

Decisions to confirm

  • Declarative JSON graph, not workflow-as-code. The two in-process alternatives (Vercel Workflow DevKit, DBOS) are code-first; a graph an agent can write as data and a run view that knows the shape up front both need the declarative form.
  • Definition files in JSON, not YAML, to avoid a parser dependency. A $schema key gives editor completion.
  • Expressions are sandboxed JS predicates in node:vm, not a custom language and not an out-of-process runner. The sandbox exists for determinism, not as a security boundary.
  • No external engine (Temporal, Inngest, n8n). The interpreter is a few hundred lines and fits the "small enough to understand" rule.
  • Every wait expires. Default 3 days for human; wait_event requires an explicit timeout.
  • Triggers are rows, not definition state. Files may declare them as a convenience and the loader owns those rows; everything created at runtime lives only in the table. Workflows declare an inputs schema and read inputs.*, never the trigger's shape.
  • @xyflow/react + @dagrejs/dagre are the only new web dependencies.
  • Feed-triage reply-by-number is modelled as a long-lived human wait on the same run rather than a separate email-triggered workflow. A night's run stays waiting until the reply or a 7-day expiry, which is also what the run list should show.
